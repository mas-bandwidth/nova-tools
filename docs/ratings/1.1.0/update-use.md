# nova-update USE rating, nova-tools 1.1.0

Rater: deepseek-v4.1-flash
Build: 3eb1c1bca1fc
Score: 7/10

## Reasons
The core is a good AI tool. `nova-update help` answers the three questions in fourteen lines and the `example:` block runs as printed: `nova-update example --out versions.tsv`, then `report`, `status`, `apply --dry-run` and `version` each exit as the help says and write nothing outside the named path. A cold reader gets a real end-to-end job in one turn: a manifest under the scratch directory with an installed script and a `local:` latest, `check` prints STALE at exit 1, `apply` runs the install argv and reads the version again, and the next `check` is current at exit 0; a second job through `apply --version` and a `{version}` template completes and rechecks the same way. Manifest errors are the best part: a file with a bad kind, an empty owner and a seventh field is refused in one line naming lines 4, 5 and 6, each with what the field wants. Refusals end with `run:` and the next command, UNKNOWN is never OK, `--json` carries the same facts and items as the lines, `apply --dry-run` prints the plan and writes nothing, and a bounded listing prints `MORE shown=<n> total=<n>` with the flag that raises it.
The score loses for: the release half contradicts its own help (the flag text says "such as 1.2.0" and every release verb refuses 1.2.0 for not being v-prefixed); `release install` has no effect line and no `--dry-run` although the exit-code text promises one; a bad `--store` address dials five times and leaks the Redis client's pool log to stderr before refusing; independent flag problems are reported one at a time while manifest problems are reported together; and the line rendering of a NO result goes to stderr while its `--json` goes to stdout, so a reader that captures stdout sees nothing. A 10 needs the release examples to run, a dry run and an effect line on every writing verb, input validated before a dial with no library noise, every independent problem at once, and one stream for both renderings of the one result value.

| 1 | `nova-update release build --version 1.2.0 --out ./out --source .` | the flag's own help says the version is "such as 1.2.0", and that exact value is refused: `BUILD REFUSED: the version "1.2.0" is not v-prefixed (pass --version vX.Y.Z)`; `release cut` and `release pull` refuse it the same way, so the example an AI copies first fails | write the usage and the flag text as v1.2.0, or accept the bare form | S |
| 2 | `nova-update check --file many.tsv` | the line result of a NO run goes to stderr: with stdout alone the run prints nothing, while `nova-update check --file many.tsv --json` prints the same result on stdout; the two renderings of the one value land on different streams, so a reader that captures stdout misses a stale manifest | print the line rendering to stdout as the JSON rendering is, or say in the banner that a NO result is on stderr | M |
| 3 | `nova-update release install -h` | the verb help has no `effect:` line and offers no `--dry-run`, although the exit-code paragraph promises a dry run printed its plan and the standard gives every writing verb a dry run; `nova-update release install --from ./nope --version v1.2.0 --bin ./binx --dry-run` answers `INSTALL REFUSED: unknown flag --dry-run (the verb's help lists its flags)` | add the effect line and a --dry-run that prints the install plan and writes nothing | M |
| 4 | `nova-update report --store notanaddr` | a malformed store address is not refused before the dial: the run prints five `redis: ... connection pool: failed to dial` lines from the client to stderr and only then `REPORT REFUSED: fleet beats at notanaddr: dial tcp: address notanaddr: missing port in address`; the reader gets library noise and a slow retry for a value the tool can check itself | validate the host:port before dialing and keep the client's log off the tool's stderr | M |
| 5 | `nova-update check --file versions.tsv --max abc --kind bogus` | two independent bad flags are reported one at a time: the run names only `--max`, and swapping the order names only `--kind`; the manifest path reports every problem at once, so flag values are the weaker half of the same promise | collect flag-value problems and print them together with the `run:` line, as the manifest path does | S |
| 6 | `nova-update check -h` | the verb help is not scoped to the verb: it repeats the whole six-line THE MANIFEST lecture from the top-level help before the effect and the three flags, so the answer to what `check` takes is 25 lines from a reader who asked about one verb | print the verb's usage, effect and flags, and link the manifest lecture once from the top-level help | M |
| 7 | `nova-update example --json` | the one verb whose value is not facts and items: its JSON carries the manifest as a single escaped `payload` string instead of `items`, so an AI must unescape a tab-separated blob where every other verb gives typed rows | render the example manifest in the same value shape as the other verbs, or say in the help that `example --json` is a payload | S |
| 8 | `nova-update release cut -h` | the default for `--receipts` is a path under a specific user's home directory that a cold reader does not have, and the same default is repeated in the prose; the reader cannot tell what to pass instead except that the gate is skipped | name the default as a role or an environment variable, and print the remedy when it is absent | S |

## Good, keep
Manifest errors reported together, each with its line and what the field wants: `nova-update check --file bad.tsv` names lines 4, 5 and 6 in one refusal.
The local-first core: `example` runs from the binary, `check` and `report` read a hand-written manifest, `apply --dry-run` prints the plan, and `apply` runs one named install and rechecks the version, exit 0 when the box moved.
`--json` is the same result value as the lines, a bounded listing prints `MORE shown=<n> total=<n>`, and UNKNOWN is FAILED at exit 1, never OK.
