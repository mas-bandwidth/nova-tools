# nova-update READ and USE rating, nova-tools 1.2.0

Rater: Zhi, a DeepSeek worker (deepseek/deepseek-v4) running the dsh harness, dealt a friend's re-rate card
Build: 9c9b2ebc49fd
READ: 7/10
USE: 7/10

No v1.2.0 tag exists on the forge yet (the newest is v1.0.0), so this rates the release candidate at the head of sprint/mechanical-2026-10-02. `nova-update version` prints `nova-update v1.0.1-0.20261007202756-9c9b2ebc49fd linux/amd64 go1.26.6`. The help was read cold first (`nova-update help`, every manifest verb's `-h`, `help release` and every release verb's `-h`), then docs/SPEC-UPDATE.md, then the tool was used for real on a Linux bench in a scratch directory with fake tools on a scratch PATH: no live store, no server, no real bus, no forge.

## Reasons

READ. `nova-update help` opens with one sentence of purpose, a how-it-works, the usage block, the defaults, the exit table and five examples; every manifest verb's `-h` quotes its usage line from help, carries an `effect:` line, and lists its flags with what each wants; refusals name the flag and the next command and exit 2. A cold reader can go from the binary alone to a working first run in a minute, and the example prints the next command. What keeps READ at 7 is that several help and spec sentences are still not true of the binary. The banner says "check and report compare the two" (internal/update/cli.go:165) while `report -h` says "reads each installed version, no latest, no network". Help and the spec grammar say a result's first line is `OK`, `FAIL` or `REFUSED` (internal/update/cli.go:199; docs/SPEC-UPDATE.md:630 and :645), but the binary prints `CHECK FAILED`, `REPORT FAILED`, `APPLY FAILED` (internal/update/out.go:30), so an AI matching the documented word misses every failure line. The spec opens "One tool, three verbs" (docs/SPEC-UPDATE.md:6) over four verb bullets; calls a thirteen-line block "Those ten usage lines" printed "byte for byte" (:412) although `help` prints thirteen `nova-update` lines and the block omits the banner's `version` line; and says "its five usage lines" and "Five verbs" (:415, :440) while `help release` prints six, cycle included. The top usage line names five release verbs (internal/update/cli.go:146). Every release verb's `--version` help says "such as 1.2.0" (pkg/release/cli.go:242) and `release install` refuses exactly that spelling as not v-prefixed (pkg/release/release.go:227). The release half is still a wall: each note is a single paragraph of several hundred to about 1,800 characters about a coordinator, a dogfood gate and a fleet play, repeated under every verb that shares it.

USE. The manifest verbs are the strongest part of the tool, and most of the trial ran on them. `example --out` writes, says `unchanged=true` on a second run, and refuses to overwrite a foreign file. `report` reads only the installed side and prints the identity raw beside the key, exit 0, with no network. A manifest with an unknown kind and a short line was refused once with both problems, each with its line and a remedy. `check` and `status` line and `--json` forms carry the same facts. On fake tools, a local upgrade ran end to end: `check` said STALE, `apply --dry-run` printed the resolved argv and started nothing, the real `apply` printed BEFORE, RUN and AFTER and moved the tool from 0.1.0 to 0.2.0, and the next `status` said EQUAL. An installer that changed nothing was caught by the re-read: `APPLY FAILED ... installed 0.1.0, asked 0.2.0`, exit 1. A missing command was `CHECK UNKNOWN ... not_found` with the PATH it searched, exit 1. Every refusal provoked named the fault and the remedy at exit 2, including no `--file`, a bad `--kind`, `--max -1`, a name the file does not carry, an apply of `none`, and a `--dry-run` passed to `check`. What keeps USE at 7 is a handful of real hazards. `release build --out <relative> --source <checkout>` run from any other directory compiles the tools with `go build -o <relative>/...` under `cmd.Dir = source` (pkg/release/edges.go:289, composed at pkg/release/build.go:218), so the 24 binaries land in the source checkout, the caller's own directory gets an empty `SHA256SUMS`, and the run ends `BUILD REFUSED: the SHA256SUMS just written cannot be read back: SHA256SUMS lists no artifact`, exit 2, leaving the checkout dirty. `apply` on an entry already equal to its target runs the installer anyway (internal/update/cli.go:702): the second `apply` of an equal tool ran the install command again. A pin row written with the help's own `local:go version` answers `STATUS EQUAL ... installed=version latest=version`, exit 0, `pins=0` (internal/update/read.go:72). `report --send` with no `nova-bus` on PATH says `sent=uncertain` and `send not confirmed: not_found` (internal/update/report.go:190) when nothing could have been sent. A header-only manifest is `CHECK OK checked=0`, exit 0. `Compare` orders only equally long release tags (internal/update/read.go:396), so a real jq 1.6 against 1.8.2 is DIFFERENT, never STALE. And `apply --version 0.1.5` prints `APPLY BEFORE ... latest=0.1.5`, the asked target, under a source that answered 0.2.0 (internal/update/cli.go:702).

A 10 would make every help and spec sentence true of the binary (`FAIL` or `FAILED`, the six release verbs, the version shape, the byte-for-byte block); resolve `--out` and `--source` to absolute paths once; make an `apply` at its target a no-op unless asked; read a pin's version-shaped token; say a missing nova-bus was not found and `sent=no`; refuse a green over no entries; order versions of unequal length; keep a watch pass on one stream; give the release verbs `effect:` lines, shorter notes, and a `--dry-run` for install; and name a model's tag rather than its entry name in the refusal.

## Good, keep

A manifest refusal names every problem of the file at once, each with its line number and a remedy, then one `run:` line, exit 2 (an unknown kind and a short line were fixed from one answer).
The apply loop re-reads the installed version after the installer and fails when it did not move: `APPLY FAILED ... installed 0.1.0, asked 0.2.0`, exit 1.
`apply --dry-run` prints the same resolved argv the real run uses and starts no process; `example --out` is idempotent (`unchanged=true`) and never overwrites a foreign file.
`report` reads the installed side alone, prints the raw identity beside the key, and needs no bus or network.
The refusals that were provoked (no `--file`, an unknown kind, `--max -1`, a missing name, an absent name, an apply of `none`, an unknown flag, an unknown verb) each named the fault, the flags or names that exist, and the next command.
`check`, `status` and `report` render one value as typed lines or as one `--json` object.
