# nova-table READ and USE rating, nova-tools 1.2.0

Rater: z-ai/glm-5.3-flashx in opencode, a sprint worker on a friend's re-rate card this file is named for
Build: 1b2c8aea22f1
READ: 8/10
USE: 6.5/10

No v1.2.0 tag exists on the forge yet, so this rates the release candidate at the head of sprint/mechanical-2026-10-02, commit 1b2c8aea22f1. `nova-table version` prints `nova-table v1.0.1-0.20261007210909-1b2c8aea22f1 linux/amd64 go1.26.6`. Built and run on the card's own machine, in a scratch trial directory; no live store, and no server started, because the card forbids starting one here. The root help (127 lines), the guide and all 35 verb, subverb and version `-h` pages were read cold (`help -h`'s refusal read with them). Then the tool was used for real the one way this machine allows: every write verb ran under its own `--dry-run`, a nine-line `shell --dry-run` session ran from a pipe, `batch --dry-run` planned a manifest, and every read verb, `watch --once` and plain writes were run against a dead Unix-socket path to exercise the unreachable-store refusal, which repeated the banner's throwaway-store recipe with the address it tried. About ninety calls in all. The store-side findings below were each confirmed at source at this head, and the tool's tree (cmd/nova-table, internal/ntable, internal/nsprint) is byte-identical to the build the two earlier 1.2.0 ratings verified against a live throwaway store (empty diff since 9c9b2ebc49fd), so their live behavior carries.

## Reasons

READ. The banner says in one line what the tool is and in five lines how it works, names the store it needs, gives a store-less `--dry-run` example, and prints a four-line throwaway-store recipe. Every `-h` page has usage, an example, its flags grouped as flags / connection / write epoch and receipt where it has them, exit codes and an `effect:` line. The help layers work: `help cell`, `cell -h`, `help cell add` and `--version` all answer, and a bare command refuses in one line naming the verbs. An unknown verb, subverb, flag or argument count is refused in one line with the full list and a `run:` line naming the verb's page; a near-miss flag names the nearest.

What keeps READ at 8. The banner is 127 lines and the column grammar, fold table, epoch rules and shell rules still come before the `example:` block. The same 385-character `effect:` sentence is repeated on every write page, and on the view pages and shell it names the table, its epoch, its rows and columns, and a bound cell, none of which a view has. `--score` and `--at-epoch` print as `<string>` where the usage lines say `<n>`. The banner's own line says `render` prints nothing at all when the table is empty, while the guide's empty rule and the renderer draw header, rule and footer. Help never says member records are shared by every table on the default prefix, that a new epoch starts with no rows, or what `check` checks. Dated quotations of the owner are still in eight comments of the package. And `help -h` and `help help` are refused by the very door every other refusal names.

USE. The tool is usable for real with no store at all, which is the one use this machine permits: `--dry-run` on every write verb makes every check the real run makes before sending and prints the exact call (`sends="FCALL ns_table_create"`, `dialled=0 written=0`), the dry `shell` planned create, row add and cell add from a pipe and refused a read line by dialling, exactly as its help says, and `batch --dry-run` planned the manifest with `members=1 changes=1 guards=0`. Every refusal met named the problem, the valid alternatives and one runnable command; the unreachable-store refusal repeats the whole recipe with the address it tried; `--redis mem:` is refused with why it is not an address. A bad `--score` value, a bad `--at-epoch`, a bad `--every` duration and a missing `--columns` were each refused with what the input wants. `member read --json` prints one JSON object even for a refusal. The store-side faults below were live-verified by the two earlier 1.2.0 ratings on a byte-identical tree and confirmed at source here: a dead end after a plain drop, member identity shared across tables so `batch -h`'s own example fails on a worked store, silent no-op removes and moves, a hidden table dropped from a watch frame in silence, a literal `-> ETA` with no value, and `--json` still on two verbs only.

What keeps USE at 6.5, the deepseek rating's ground: the same traps stand. To reach 10 it needs the drop, create and set loop closed, member identity scoped the way the help implies or the scope said, no-op writes that say they did nothing, `--json` on the reads, and a store-free way to run the reads end to end.

## Good, keep

The store-free surface is real and honest: `--dry-run` on every write verb makes every pre-send check the real run makes, prints the exact FCALL with `dialled=0 written=0`, and refuses a bad column spec exactly where the real run would; the dry `shell` plans write lines from a pipe, still reads for read lines as its help says, names the failing input line, and refuses a line that turns the dry run off. Every refusal met named the problem, the alternatives and one runnable command; the unreachable-store refusal repeats the whole throwaway recipe with the address it tried. Layered help (`help cell`, `cell -h`, `help cell add`) answers with no store, every page carries usage, example, grouped flags, exit codes and `effect:`, and a near-miss flag names the nearest. `member read --json` renders one JSON object for results and refusals alike. `batch --dry-run` plans the manifest with member, change and guard counts.
