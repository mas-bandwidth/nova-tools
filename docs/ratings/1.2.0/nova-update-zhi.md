# nova-update READ and USE rating, nova-tools 1.2.0

Rater: a Claude worker, cold to this tool, on a friend's re-rate card
Build: adc585d68173
READ: 7/10
USE: 7/10

No v1.2.0 tag exists on the forge yet, so this rates the release candidate at the head of sprint/mechanical-2026-10-02. `nova-update version` prints `nova-update v1.0.1-0.20261007015850-adc585d68173 linux/amd64 go1.26.6`. Built and run on a Linux bench machine in a scratch directory holding the fixtures a stranger starts from; no live store, no server, no bus, no forge.

## Reasons

READ. `nova-update help`, every manifest verb's `-h`, `help release`, every release verb's `-h` and docs/SPEC-UPDATE.md end to end were read cold. The banner says what the tool does in one line, a how-it-works with the manifest described, a first run that works from the binary alone, then the verbs block byte for byte, the defaults, the four notes that explain the snapshot, the locals and the two-binaries pairing, the manifest's six rules and the example block. Each verb's `-h` carries an `effect:` line in the language of three classes (inspection, local write, delivery) and lists its flags. The binary refuses with one line each, the fix being a paste back into the shell. The example is the one-prose first run.

The first place of confusion is `internal/update/cli.go:165`: "check and report compare the two; apply runs one named entry's command and reads the version again, nothing else." `report -h` says it reads installed only, no latest, no network; the spec says the same in rule 20; `status` is the verb whose every entry is shown. The first place of doubting a claim is the output grammar: the help (`cli.go:199`) says a first line is "OK, FAIL or REFUSED" and the spec's grammar at `docs/SPEC-UPDATE.md:630` says `CHECK <OK|FAIL>`, but the binary prints `CHECK FAILED`, `STATUS FAILED`, `APPLY FAILED`, `REPORT FAILED` (`internal/update/out.go:30`). The first place of boredom is the release half: the top usage line lists five release verbs (`cli.go:146`) and `help release` lists six with cycle (`internal/release/cli.go:178`); each release verb's `-h` paragraph runs several hundred characters about a coordinator, a dogfood gate and a fleet play, all of which a reader checking their own manifest never needs. The spec opens "One tool, three verbs" (`docs/SPEC-UPDATE.md:6`) and lists four; it says "five usage lines" (`SPEC-UPDATE.md:415`) and "Five verbs" (`SPEC-UPDATE.md:440`) for six release verbs. The whole release half is felt: the banner is a wall this tool has not earned yet.

USE. Everything below was run on a scratch directory on a scratch HOME, holding the example manifest and small fixtures. `example --out versions.tsv` writes the example with `unchanged=false`, a second run says `unchanged=true`, and `example --out other.tsv` writes a different name. `report`, `status`, `check` and `apply go --dry-run` ran on a clean manifest, each exit 0 and the count line a single source of truth. `status` shows the current entries too; `check` hides them. `--json` on `check`, `status`, `apply`, `report` and `adoption` returned one object from the same value as the typed lines. Several refuse paths were exercised: missing `--file` (named once, with `refusing to guess` and `run: nova-update check -h`), an unknown verb (named with all nine), an unknown flag (named with the verb's full flag list), `--max -1` (named the wanted shape), `--kind weights` (named the wanted shape), `--file` pointing to a directory (named), five problems of one manifest (bad locator, seven fields, empty apply, each with its line, in one refusal), a manifest with no header (named line 1 with the put-it-back remedy), `apply` with no name and with the wrong-case name `G` and `gh-cli` (named the file and the entry count names), `apply` of a `kind=model` entry (named the model and the owner's `ollama pull`), `apply --version` against a register with no `{version}` (refused), `apply` of `none` (refused, "installed by hand"), `apply` against a manifest whose latest source is `github:cli/cli` and with `--version 9.9.9` (planned against `9.9.9`, the asked version), `report --send` without `--as` and `--to` (named both, in one refusal), `report --draft --send --as x --to y` (refused for exclusivity), `watch` over three checks (one OK, one OK, one REFUSED and an ESCALATE), `adoption` over a six-row ledger with `--as me` and `--json`, `adoption` with a bogus state (named the eight valid states), `release install --version 1.2.0 --bin /tmp` (refused: not v-prefixed), `release pull --version v1.2.0 --out /tmp --changelog /tmp` (refused: no SHA256SUMS at the path, named the build command).

What held the score at 7. The example manifest's own `apply` cannot succeed end to end: its apply argv is `go install golang.org/dl/go{version}@latest`, a wrapper that never reads in `go version`; with the help's default `--timeout 5s` and the real network, it timed out at 5.057s with `APPLY FAILED ... took=5.057s: timeout` and no remedy naming `--timeout`. `watch` puts `ADOPT OK` on stdout and `ADOPT REFUSED`, `ADOPT ESCALATE` and `ADOPT DONE` on stderr; a caller reading only one stream loses the refused and the receipt. The `ESCALATE` line says "duty files an issue and a fix card" while `watch -h` says this tool files nothing, so a watchdog reading only stdout would never see that part. `APPLY BEFORE` echoes `latest=<asked>` rather than `latest=<source>`, so for a manifest that reads both sides (the example does), `<asked>` differs from what was probed and a reader's line does not match the source it walked. With `--version 9.9.9` against a source that answered `2.102.0`, the line reads `latest=9.9.9`, the asked. The status word on the count line is `FAILED`; the help and the spec say `FAIL`. A kicker: `--draft --as me` (no `--to`) prints `missing --to` and the rest of `report` exits 2; fine, but the spec/banner says the same `--as/--to` block is what `--send` takes, and the meaningful distinction (compose vs. deliver) is what a caller wants to see on the line.

A 10 would: an example manifest whose `apply` is `none` (or whose target is reachable in five seconds); one stream for a `watch` pass, or `--json` receipts across stdout and stderr-equivalents; one spelling of `FAIL` across binary, help and spec; the release pipeline's surface stated once and correctly (six verbs) in the usage line, the help, and the spec; the banner mention `status` rather than `report` as the verb that lists every entry's line, current ones too; the apply `latest=` line echo the source's answer (`installed=`, `latest=<source>`, `target=<asked>`) and refuse `--version` against a register whose source answered `latest=` is the asked; the `--send` and `--draft` lines name their action in the message so a reader knows before the bus process that it was a deliver or a compose.

## Good, keep

Refusals that name every problem of an invocation at once, each with its line and remedy, then one `run:` line. A 5-problem manifest was fixed from one answer. `apply` prints `BEFORE`, `RUN` with the resolved argv, `AFTER` re-read against the target, with `--dry-run` printing the same command and starting no process. `example --out` that never overwrites and says `unchanged=true` on a rerun, and a first run that works from the binary alone. One `--json` envelope on every manifest verb, with the count line as facts and items as typed rows. Pin reads the second token of the first line (rule 15); a pin with a local argv whose first line is `PIN <v>` reads `<v>` and reports EQUAL or DIFFERENT correctly. The 64 KB output cap and `not_found` reason name the PATH searched, so an `argv[0]` resolving nowhere tells the reader the box that refused. Every release verb refused the spelling `1.2.0` and names `v1.2.0` (the v-prefix check itself is right; the help sample disagrees with it). `nova-update version --bogus` is refused as an unknown flag with the verb's only flag listed, so a misspelled version verb no longer prints the flag package's own sentinel. `release install --from <dir> --version vX.Y.Z --bin <dir>` refusal names the build command when there is no SHA256SUMS at the path.
