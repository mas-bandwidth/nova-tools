# nova-redis READ and USE rating, nova-tools 1.2.0

Rater: qwen3/qwen3.7-flash in opencode on a friend's re-rate card
Build: e174cc87f042
READ: 8/10
USE: 8/10

No v1.2.0 tag exists on the forge yet, so this rates the release candidate at the head of origin/sprint/mechanical-2026-10-02 as origin held it when staged, e174cc87f0423afed166821d0962e0a6513f4ad1. The binary was built on this Linux machine and run against an existing Redis server listening on 127.0.0.1:6379 for functional exercise; nothing live or production was touched. Every verb was examined (`nova-redis help`, each verb and sub-verb `-h`); `serve --dry-run`, `spill --dry-run`, `acl render`, `fn load`, `fn check`, `acl check`, `acl apply --dry-run`, `install store --dry-run`, `uninstall store --dry-run` were all tested; `spill` and `recall` exercised a real store with JSON output, refusals, and expiry paths. The spec (docs/SPEC-REDIS.md) was read cold alongside the code (cmd/nova-redis/{main,serve,fn,acl,install}.go).

## Reasons

READ. The tool is exceptionally well-documented: every verb answers `-h` and `help <verb>` with usage, flags, effect classification, exit codes, and often examples. The banner gives what the tool does in one line, explains how it works in four concise bullets, and provides a throwaway recipe that runs without any infrastructure beyond redis-server on PATH. Refusals are excellent — they name every problem at once (missing --owner, empty owner, missing --ttl, bad address shape) and carry a runnable `run:` breadcrumb. `--json` is supported on nearly every verb that produces structured output, rendering the same Go value as both lines and JSON. The dry-run support covers serve, spill, acl apply, install store, install bus, uninstall store, and uninstall bus, letting a reader see what a verb would do before committing to it. Passwords never appear in arguments or printed output; the SHA-256 hash is used instead of plaintext. ACL rendering opens no store, making `acl render` immediately useful for previewing user definitions. The spec (docs/SPEC-REDIS.md) aligns well with the binary: exit codes, refusal grammar, key ownership model, persistence rules, and the bound-to-loopback-tailnet-only constraint are all stated clearly.

What keeps READ at 8. The `version` verb's `--json` output puts its version string in `payload` rather than structuring it into individual facts (version, os, arch, go version); a consumer has to parse the payload string to extract components. Several example blocks are empty strings despite the verbs having natural first runs worth exemplifying (`fn load`, `fn check`, `acl check`, `acl apply`). The `--addr` flag is deprecated in favor of `--redis` but still prints a NOTE even when the user already knows it's deprecated — not harmful, just noisy. The `spillage_recipe_test.go` recipe in the help text uses bare bash variable expansion (`$d`) which could confuse AI readers who might not know to substitute it.

USE. Functional testing was clean: `spill --json` wrote a key and returned `{"result":{"verb":"spill","status":"ok","exit":0},"facts":{"key":"worker:note","ttl":"10m0s","expires":"...","bytes":11}}`; `recall --json` read it back with the exact value. A missing key returns `MISSING` at exit 1 with a fact `key`; a TTL-refused key returns `UNBOUNDED` at exit 1 with a remedy note. `acl render` correctly listed all 12 key families and 4 role-based users with their function permissions without connecting to any store. `fn load` connected to the running store and reported `REPLACED nova_sprint sha=... was=... library loaded`. `serve --dry-run` validated binding, port, directory path, and ACL structure without creating anything. `install store --dry-run` produced a complete systemd unit file ready for inspection. Refusal paths work end to end: missing `--owner` names the requirement and the constraints (no colon, no whitespace); missing `--ttl` says why bounded keys matter; an empty address refuses with a named flag.

What keeps USE at 8. When `fn load` ran against a store that had a different library digest (90266b4d → 5ad34e43), it REPLACED silently without any confirmation prompt or warning about overwriting an existing deployment. On a shared or pre-provisioned store this could erase another team's function library unexpectedly. This is by design per fn.go comments ("it replaces other code under the library's name") but a friction point for safe adoption. `recall UNBOUNDED` fires when a key exists but carries no TTL — this is correct (unbounded keys are bugs) but a human-created key via redis-cli might confuse a reader expecting EXPIRED or MISSING rather than a bug-report verdict. The default store directory for `install store/bus` (~/nova-bench/redis/store and ~/nova-bench/redis/bus) requires the caller to either provide --secrets login or export NOVA_REDIS_PASSWORD, and neither error path is surfaced during the install command itself (the password check happens inside serve at launch time).

## Good, keep

Refusals are the best part: every independent validation failure is collected and reported in one run, each with a message saying what the flag wants and why there's no default. The refusal grammar is consistent (`REFUSED: <reason>; run: nova-redis help`), exit codes are truthful (0=done, 1=ran-no, 2=could-not-run), and passwords never appear in printed output or arguments. Dry-run support is comprehensive across all mutating verbs, letting readers verify plans before execution. `acl render` opening no store is a great UX pattern — immediate feedback without network access. `spill` and `recall` enforce the owner prefix + TTL contract at the code level, preventing the most common Redis misuse patterns. The SHA-256 hashing for the default ACL user (never the plaintext password) is a good security practice. The bind validation accepting only loopback and tailnet addresses prevents accidental exposure.
