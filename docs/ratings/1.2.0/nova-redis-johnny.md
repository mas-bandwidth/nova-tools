# nova-redis READ and USE rating, nova-tools 1.2.0

Rater: Grok. Harness: Grok Build. Model: Grok.
Build: 3a75f59adf46
READ: 7.5/10
USE: 8/10

Question: Is this a good tool for an AI to use?

## Reasons

Read cold from `nova-redis help`, `help <verb>`, every verb's `-h`, and docs/SPEC-REDIS.md, then used on a throwaway Redis bound to 127.0.0.1 on a Linux bench. Not port 6379, 6380, 6381, or 6390. The live spill and recall lines in the banner's example were not pasted: they name 127.0.0.1:6379, and that port was not this card's store. The dry-run form of that line was run; it returned in a few milliseconds with `written=0`.

READ 7.5. The banner says what the tool is, how serve, spill, recall and the function verbs work, where the password comes from, and that the dry-run needs no store. Every verb's `-h` quotes its usage, lists its flags with what they want, and ends with an effect line. A bad spill names every problem in one run and ends `run: nova-redis help`. The spec now lists the acl verbs and maps each rule to a test. What keeps it from a higher score is that several of those texts are wrong in a way an AI acts on. `spill -h`, `fn load -h` and `acl apply -h` say `effect: local write: writes files on this machine`, and none of them writes a local file (finding 2). The banner's first-run sentence says spill and recall need a Redis at 127.0.0.1:6379, and the example's next lines are live writes to that port (finding 8). The banner says the password comes from the variable `NOVA_REDIS_PASSWORD_ENV` names, else `NOVA_REDIS_PASSWORD`; `serve` reads only `NOVA_REDIS_PASSWORD` (finding 7). Help and the spec say `--addr` is `<host:port>` only, while a Unix socket works (finding 13). The spec's dialling list omits acl check and acl apply, and it says an unreachable store is one FAIL line; spill and recall print REFUSED (finding 14). Every `-h` repeats the whole tool's exit table, which never mentions an acl outcome, and the top help still promises `--max` for a verb that lists, when no verb here lists (findings 15 and 16).

USE 8. On the throwaway store the jobs an AI actually has all finished. `spill --dry-run` printed one `SPILL OK` line, `written=0 dry_run=true`, and the same facts as one JSON object, with no dial. A real spill and recall round-tripped `hi`, a value with spaces and quotes, and a value with a newline: the line hex-escapes, `--json` has the bytes exactly. An empty value came back as `value=-` on the line and `""` in JSON (finding 9). A 2s TTL was `RECALL OK` at once and `RECALL MISSING` exit 1 three seconds later. `fn check` on an empty store was `MISSING` exit 1 with a pasteable `fn load` remedy; `fn load` printed `LOADED`, the next check `OK`, the next load `UNCHANGED`. `acl render` exits 0. `acl check` on a store without those users was `ACL CHECK DRIFT` exit 1. `acl apply` with no password source was `ACL APPLY REFUSED` exit 1 and wrote nothing; with one variable per missing user it printed `ACL SET` for four users and `ACL APPLY OK ... set=4`. A second apply set nothing. `spill` as the new `coordinator` user wrote and `fn check` as that user was `OK`. `serve --dry-run` printed the plan and created nothing. A real `serve` on a fresh directory, after redis-server's own ready line, took a spill; SIGTERM exited 0 with `SERVE STOP`; a second `serve` on the same directory recalled the same bytes. `acl apply` against that server saved `saved=acl-file`. Refusals on the real path are specific: `--ttl 10` says `try 10m`, `--owner sprint` names the store family, a closed port says start the store or correct the address, a wrong password says the login was refused and names the variable.

What keeps USE from 9 is the safe path lying, and two store-admin paths sending the reader the wrong way. `spill --dry-run` with a password variable that is not a name, and the same dry-run with `--user` whose variable is empty, do not print those problems. Both exit 1 with `SPILL FAILED: --dry-run was given and the verb never read it (Call.DryRun); it may have written` (finding 1). Nothing was written; the line says it may have been. `acl check` and `acl apply` against a closed port exit 2, but the remedy says to log in as a user who may run ACL commands, which was never tried (finding 5). `fn check` on that same port says the store did not answer. `acl apply` with four missing users lists all four in `missing=` and puts only the first in the `run:` command (finding 6). `SERVE START` is printed before the server accepts connections, and redis-server's log, including 266 ACL deprecation lines after the rendered rules are saved, is mixed into serve's stdout (finding 3). After `ACL SAVE` the ACL file was mode 0644; serve had written it 0600 (finding 4).

Not run: the banner's live spill and recall against 127.0.0.1:6379, and `acl apply` aimed at any store this card does not own.

## Good, keep

`spill --dry-run` is a bounded plan: key, ttl, expiry, bytes, store and `written=0` on one line, and the same facts as one JSON object. It does not dial.

A spill line with several bad fields exits 2 and names each one. `--ttl 10` says `try 10m`. `--owner sprint` names the store family and says scratch lives outside it.

`fn check`, `fn load`, `acl check` and `acl apply` do what the words say on a real store: MISSING then LOADED then OK then UNCHANGED; DRIFT, then a refusal that writes nothing, then SET, then a second apply that sets nothing. `acl apply --dry-run` prints four `ACL WOULD-SET` lines and exits 0 with nothing listening.

`serve --dry-run` refuses a wildcard bind, a port of 0 and a relative directory in one run, and refuses `--users` when the ACL file lacks that user, before anything starts. A real serve, stopped with SIGTERM, exits 0 with `SERVE STOP`, and a restart on the same directory recalls the value. The password was not in serve's stdout or stderr, and not in the ACL file serve wrote.
