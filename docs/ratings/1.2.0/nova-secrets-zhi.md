# nova-secrets READ and USE rating, nova-tools 1.2.0

Rater: Claude Opus 5.5 in Claude Code, a sprint worker on a friend's re-rate card
Build: dd75bc2c9f80
READ: 6.5/10
USE: 5.5/10

No v1.2.0 tag exists on the forge yet, so this rates the release candidate at the head of sprint/mechanical-2026-10-02. `nova-secrets version` prints `nova-secrets v1.0.1-0.20261006152019-dd75bc2c9f80 linux/amd64 go1.26.6`. Built and run on a Linux bench machine with real sops and age, with HOME pointed into a scratch directory and the store and its bare remote made there; no live store, no server, no gh call. ssh was a stub script for one real `place`. The rater had seen another worker's report on an earlier build of this tool; every finding below was run again on this build.

## Reasons

READ. The one-line summary and the `how it works:` paragraph say what a store, a seat and a recovery key are before any verb, and `setup:` is a paste-able block that makes a store from an empty directory. Every verb answers `-h` with the banner lines for that verb, an `effect:` line, and one line per flag that names what it wants. exec's and check's `-h` carry a full store prerequisite with why and the next command for each refusal. Refusals use one grammar, `SECRETS <VERB> REFUSED: <why>; run: <next>`, and an unknown verb or flag lists the valid ones.

What keeps READ at 6.5. The help says things the binary does not do. check's `effect:` says it decrypts this seat's file with --key to prove it opens, and a key that opens nothing passes (finding 2). The `first value:` line cannot run after `setup:` (finding 1). Three verbs give three different first-value remedies, and two of them are refused. Every example hard-codes `/opt/homebrew/bin/sops`, which is absent on Linux, while the flag lines say `command -v`. keygen's NOTE and NEXT lines, printed in setup's first step, tell the reader to add "two lines" (three are printed) and that seat add fills a `<recovery key>` placeholder in a rule for the recovery key itself. setup works only because a shell redirect makes an empty .sops.yaml before keygen reads it. The `-h` excerpts strip the indentation from continuation lines, so `--only <NAME,...|all> ...` reads as a usage line of its own. `seat -h` prints the whole root banner. One exit-code paragraph about check and exec's 125 is printed under every verb. The package doc says four verbs, the spec says two hundred lines of Go (the command and package are 6122 non-test lines), and docs/CLI.md still opens on a gate example.

USE. Once a seat file exists, the core loop is good. `exec` put exactly the named value in a child's environment and printed one OK line naming the seat, file and head; the child's own exit passed through (`false` gave 1); a missing command, no command, an unknown --only name and a 0644 key were each refused at 125 with a runnable next step. `names` and `names --json` read names without a key. `seal --stdin --no-pr` and `--dry-run` work; seal refuses an empty value, a lower-case name and a missing terminal. `seat add` re-sealed a value to a new seat, and after a hand merge the new seat's key opened it through exec. `seat inject --dry-run` and `--no-pr` work. `gate` approved a new seat, refused a rule with the recovery key dropped, and refused a plaintext file that no rule matches. `place` with a stub ssh wrote a receipt and `placed` listed it. check catches uncommitted, unsealed and unpushed state with one FAIL line each.

What keeps USE at 5.5. On a new store the printed first run does not reach a first value: `seal` refuses because the seat file is absent ("never by seal, use seat add"), and `seat add` needs a source seat that already holds values, so the only way on was a hand `sops -e`. `check --as ada` with a key that is no recipient of anything is `SECRETS CHECK OK ... mine=0`, so check does not tie --as to --key. A wrong key on exec is `sops failed: exit 128`, not "this key is not a recipient". After `seal --no-pr` or `seat inject --no-pr`, exec refuses the new name until a hand fast-forward and push; inject prints no NOTE saying so. The other gaps carry over from 1.1.0: place reads gate's seven-column registry as a home and plans `path=linux/amd64/...`, gate's in-run refusals use a second grammar, `placed` on an absent receipts directory is OK count=0, and `--json` exists on names only.

A 10 would give a new store's first seat its first value in one printed line that runs after `setup:`, make check prove that --key opens --as's file, make every `effect:` line and example true and portable as printed, give each absent-seat refusal one remedy that runs, and route gate's and place's refusals through the one grammar with a `run:` line.

## Good, keep

exec is the right shape for an AI: the value goes only into one child's environment, the OK line names the seat, file and store head without the value, the child's exit passes through, and exec's own refusals are 125, apart from any child's status. Refusals carry the one `SECRETS <VERB> REFUSED: ...; run: ...` grammar and are usually runnable as printed (the 0644 key gives the exact chmod; an unknown --only name points at names). The store prerequisite in `exec -h` and `check -h` says why HEAD must equal its upstream and the command for each case. `seal --stdin` keeps the value off argv, and `--dry-run` on seal, inject and place prints PLAN lines that name file, recipients, branch and receipt without reading a value. `seat add` and `gate` together make adding a seat a reviewable commit, and gate refuses a rule with the recovery key dropped.
