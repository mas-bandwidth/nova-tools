# nova-update READ and USE rating, nova-tools 1.2.0

Rater: Claude Opus 5.5 in Claude Code, a sprint worker on a friend's re-rate card
Build: 43b487125e85
READ: 7/10
USE: 7/10

No v1.2.0 tag exists on the forge yet, so this rates the release candidate at the head of sprint/mechanical-2026-10-02. `nova-update version` prints `nova-update v1.0.1-0.20261006145252-43b487125e85 linux/amd64 go1.26.6`. Built and run on a Linux bench machine, in a scratch directory made for the trial; no live store, no server, no remote. Read cold: `nova-update help`, `nova-update help release`, every verb's `-h` (example, check, status, apply, report, watch, adoption, version, and release cut, build, install, adopt, pull, cycle) and docs/SPEC-UPDATE.md. Used for real: the help's whole example block; a manifest of fake tools (shell scripts that print a version) to drive STALE, an apply that converges, an apply whose installer does nothing, one that exits 3 and one that outlives `--timeout 1s`; pins; a four-problem manifest; every refusal shape; report with `--draft` and `--snapshot` twice; adoption; watch with a clean and a refused check; `release install` and `release cut --dry-run` with no gh on PATH. Not run: `report --send` and `--store`, watch delivery, `release build`, `adopt`, `pull` and `cycle` (a store, the bus, ssh machines or an inventory), and every network latest source (github:, npm:, brew:, ollama:); those are judged from their help.

## Reasons

READ. The banner's first line says what the tool is, the next paragraph how it works, then a full usage block, the defaults, the six-line manifest rule, the exit table and five example lines. Every verb's `-h` repeats its usage excerpt and example, an `effect:` line that says what it writes (inspection, local write, delivery), and its flags. The manifest rule is the right shape for an AI: byte-exact header, the field vocabulary, no shell, and the promise that every problem is reported at once, which held.

What keeps READ at 7. The help contradicts its own example: rule 4 says `local:<argv>` is what "a pin takes this only" (internal/update/cli.go:254), while the example manifest (internal/update/example.go:20) is kind `tool` with `local:go version` and runs green. Rule 6's example line (`none` and owner `me`) is not the line `example --out` writes (a `go install golang.org/dl/go{version}@latest` apply and owner `caller`). The usage line `nova-update release <cut|build|install|adopt|pull>` (cli.go:146) omits `cycle`, which `help release` and the bare `release` refusal both list. `adoption -h` still never names the state vocabulary; only the refusal does (`use evaluated,useful-now,tried,adopted,declined,deferred,unknown,equivalent`). Every release verb's `-h` says `--version` is "such as 1.2.0", and the verb refuses `1.2.0` as not v-prefixed. `release install -h` is still the one help with no effect line. Every verb's `-h`, `example -h` and `version -h` included, ends with the full apply-and-report exit paragraph. `check -h`, `watch -h` and `adoption -h` carry no example line where `status -h` and `apply -h` do. watch's `ADOPT ESCALATE` line says "duty files an issue and a fix card" while `watch -h` says "this tool files nothing", and "duty" is defined nowhere a cold reader looks. The spec still opens "One tool, three verbs" (docs/SPEC-UPDATE.md:6) over nine verbs, and its first sentence speaks of "this estate" (docs/SPEC-UPDATE.md:3). README.md:54 still says "These are the Nova Tools 1.0.0 commands".

USE. The core loop works as the help says. The example block ran as printed and each line exited 0 with a typed first line (`EXAMPLE OK`, `REPORT OK`, `STATUS OK`, `APPLY OK ... dry_run=true`); `example --out` over an existing file left it alone (`unchanged=true`). A fake STALE tool went BEFORE, RUN, AFTER to `APPLY OK from=0.1.0 to=0.2.0` exit 0, and `check` then said `CHECK OK`. An installer that did nothing was `APPLY FAILED ... installed 0.1.0, asked 0.2.0` exit 1; one that exited 3 was `APPLY FAILED ... exit 3`; one that slept past `--timeout 1s` was `APPLY FAILED ... timeout` at 1.065s and left no child behind. A four-problem manifest was refused with all four, each with its line and remedy. Unknown verb, unknown flag, bad `--max`, bad `--kind`, missing `--file`, missing file, absent name, `apply` with no name and an apply of a `none` entry each refused exit 2 naming the vocabulary and the next command. `--snapshot` said `changed=yes` then `changed=no`.

What keeps USE at 7. The pin reader still takes the line's second token (internal/update/read.go:71): a pin whose latest is the help's own `local:go version` reads `latest=version`, and a pin whose installed column is also `go version` is `EQUAL` with `installed=version latest=version`, so status counts a lie as current. `pins=` counts only DIFFERENT pins (cli.go:552): a file with two pins said `pins=1`. `release cut --dry-run` still asks the forge where the branch is before any plan exists, and still does when `--local-diff` names a checkout: with no gh on PATH both runs were `CUT REFUSED: cannot read dev of owner/name: gh api ...`. A watch pass with one refused check still splits across streams (ADOPT OK on stdout; REFUSED, ESCALATE and DONE on stderr) and watch takes no `--json`. `release install` still has no `--dry-run`, and its unknown-flag refusal says only "the verb's help lists its flags" where every other verb lists them. A failed install drops the installer's stderr: the `exit 3` run printed `boom` on its stderr and the tool showed none of it, so the AI learns only that it failed. `APPLY FAILED ... from=0.1.0 to=0.1.0` uses `to=` for the version found after, where the OK and dry-run lines use it for the target. An apply of an entry already current runs the installer again under `APPLY OK from=0.2.0 to=0.2.0` with no note that nothing was due. A refused manifest under `--json` puts all four problems in one `why` string instead of one per problem. From reading, not run: the example manifest's apply (`go install golang.org/dl/go{version}@latest`) installs a `go1.26.6` wrapper binary and leaves `go version` where it was, so a real apply of the help's own example cannot reach its target.

A ten needs: a pin read that takes a version-shaped token or refuses; an offline cut plan; one stream or a `--json` receipt for a watch pass; `release install --dry-run` and its effect line; the installer's stderr on a failed apply; one meaning for `to=`; an example whose apply moves what its installed column reads; and a help, spec and README that agree with the binary.

## Good, keep

The apply loop leaves nothing to infer: BEFORE, RUN, AFTER with a re-read, and a run whose installer does nothing, fails or overruns is a FAILED line and exit 1, never a quiet OK; the timeout killed the child and took 1.065s for a 1s deadline. Refusals name the problem, the vocabulary and the next command, and a manifest refusal lists every problem with its line in one run. `example --out` never overwrites. `--dry-run` on apply prints the exact argv the real run takes. Every verb but watch and release answers `--json` in one envelope. The exit contract (0 current, 1 NO, 2 could not run) held in every probe.
