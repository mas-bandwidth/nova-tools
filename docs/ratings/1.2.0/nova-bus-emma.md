# nova-bus READ and USE rating, nova-tools 1.2.0

Rater: Zhi (deepseek/deepseek-v4) in dsh, a sprint worker on a re-rate card
Build: 9c9b2ebc49fd
READ: 8/10
USE: 7/10

This rates nova-bus at 9c9b2ebc49fd, the head of sprint/mechanical-2026-10-02; `nova-bus version` prints `nova-bus v1.0.1-0.20261007202756-9c9b2ebc49fd linux/amd64 go1.26.6`. It was read cold from `nova-bus help`, every verb's `-h` and docs/SPEC-BUS.md, then built and used on a Linux bench machine against a throwaway Redis 8.0.5 bound to a Unix socket only (`--port 0`) in the job's scratch directory, stopped with `shutdown nosave` at the end; no live store was touched and no server ran on the workstation. The 1.1.0 ratings were of the git bus this tool replaced on 2026-10-04, so most of their findings are about code that is gone.

## Reasons

READ. The banner answers what the tool is, how the loop works in three lines, where the state lives (one stream per recipient under a consumer group, one log, all or none), what a first run needs, the usage of every verb, the one-JSON rule, the exit table and seven example lines. Every verb answers `-h` with its usage, a paragraph naming every line it prints and what each field means, its flags, an `effect:` line and exit codes. Unknown verbs and flags are refused with the full list and the `-h` to read. docs/SPEC-BUS.md is short and says the data, the semantics, the push gate, the identity, the ACL and the round trips plainly, including what the push proof does not prove.

What keeps READ at 8. The first-run line (cmd/nova-bus/main.go:178) says a store naming ada and bob is enough; it is not, because send and recv also need a fresh push proof for every name, and "naming" is the two sets only the spec explains. On a store that holds the names and nothing else, the banner's own example refuses `deaf:` for both names. The banner's `--max` sentence (internal/tool/tool.go:522) is not true of every listing verb: peek and names refuse it. Every verb's `-h` quotes the tool-wide exit line, which explains exit 1 by recv and wait, so send, peek, ack, log, names and version explain exits they do not have. The `--redis` text says host:port only, and the tool takes a Unix socket path too. The first place I was confused was that same first-run line; the first claim I doubted was the `--max` sentence.

USE. With the roster and the push proofs seeded by hand, the whole loop worked: send (with `--kind`, `--cc`, `--token`, `--stdin`, `--dry-run`), wait (cursor, timeout, PING and PONG skipping, a stream id refused as the wrong shape), peek (pending and new), recv (plain, `--dry-run`, `--exec`, `--all`, `--ack`, `--kind`), ack (idempotent, `--dry-run`), receipts (delivered and none), overdue (count=0 at exit 0, one message at exit 1), log (`--bodies`, `--max` with a MORE line that names its remedy) and names (proven, stale, down, none). Every verb takes `--json`, refusals included. A non-loopback address is refused before a dial, an unreachable socket names the address and the next step, a body over 1 MiB is refused, a `--exec` failure is RECV FAILED with exec_exit, and a send under one token twice prints the first line again.

What keeps USE at 7. The fifteen-minute hold is the worst: after a plain recv prints a message, or after RECV FAILED, the next recv and `recv --all` are `RECV NONE` while peek still shows the message pending, and no line says when it comes back. peek and ack answer OK for a name the roster does not hold, so a typo reads as an empty inbox. `--re` and `ack --id` take any word: `--re not-an-id` is stored and `ack --id to` is acked=false at exit 0, the same line as a real id already acked. A subject with a newline is accepted. An empty `--subject` stops at the required check and hides an empty body, a bad name and a bad kind in the same call. A garbled push proof reads as `push=none`, the same as no proof, so the remedy named is the wrong one. wait's `--json` is a different envelope, recv's `--json` payload starts with the text form's blank line, and `recv --all --json` prints one object per line against the banner. A 10 would fix the first run, say the hold, refuse a bad id and a multi-line subject, name every problem in one refusal, refuse an unknown name on every verb, tell a bad proof from none, and put wait and recv's JSON in the one envelope.

## Good, keep

The loop in three lines at the top of the banner, and the `how it works:` paragraph naming the stream per recipient, the consumer group and the one log. Send's line carries the stored body's byte count and sha256, so a sender can check a `--stdin` body arrived whole, and a trailing newline survives end to end. The push gate is described plainly, names every deaf name, and `names` shows each name's state. `login=none` makes an open store's weakness visible, and an `--as` that is not the login user is refused. The address rule refuses a non-loopback, non-tailnet store before it dials. `overdue` and `receipts` give the coordinator a real alarm. Every verb takes `--json`, refusals included.
