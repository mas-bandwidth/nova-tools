# Assignment offer / acknowledgement / decline — proposed contract

*Proposal against SPEC-WORK.md draft 28 at 7db3b95, especially the missing-verb register (lines 2353–55), Friends/CONFIG/ACTIVE (2375–91), state (983–1017), and leases/W (1316–57). It adds only the missing assignment receipt verbs. It does not define pause, stop, reconcile, worker runtime intake, transport implementation, or a new execution-state machine.*

## Purpose and invariants

An assignment has four independently durable facts: **dispatch** is the coordinator's intent to send a named offer; **delivery** is a verified report that the intended recipient received it; **acknowledgement** is that recipient's verified response; and **accepted ownership** is the coordinator's admission of that response as an assignment to a lease holder. They must not be inferred from one another. An offer neither launches work nor writes node state, task evidence, completion, an ':attempt' result, or W. A delivery receipt does not establish consent. Accepted ownership neither changes the separately tracked responsible relation nor proves that remote execution began or stopped.

The canonical session is the only writer. A bus note, launcher callback, or copied JSON is untrusted provenance data. The coordinator applies these verbs only after an operator-configured verifier returns the configured recipient identity, stable receipt id, and received-byte digest. '--as' identifies a request author, not authentication. Verifier/transport binding remains a runtime-intake decision; no credentials or verifier secrets enter a request or clip.

Each assignment has a stable 'offer_id', generated by the requester and unique in the session; 'request' remains the mutation idempotency key and is not substituted for it. Every offer also pins 'node', the node's current 'generation', an 'attempt_id', recipient friend identity, execution-profile/capability identity and revision, and a request identity. A replacement names 'predecessor_offer_id' and 'predecessor_attempt_id'; it never overwrites either lineage. Distinct offers or live attempts for one node are permitted only for the same current or proposed lease holder and separately declared capacity. A cross-holder offer conflicts with the pending or accepted holder and needs scoped reconciliation/reassignment; it cannot create a shadow lease. This preserves the source rule that two live attempts can still yield one W entry.

## CLI and request wire

All three are mutation verbs and take existing '<write flags>' exactly: '--as', optional '--request', optional '--expect', '--now', and caller wait '--deadline'. The request uses the current replay expectation rules; an imported request has a required clipped 'expect' and cannot bypass fencing.

    nova-work offer --session <path> <write flags> --node <id> --offer <offer-id>
      --to <friend-id> --profile <capability-id>@<config-revision>
      --attempt <attempt-id> --generation <n> --request-ref <opaque-id>
      --payload <pointer> --payload-sha256 <hex> --reserve <positive-slots>
      --until <UTC-stamp> [--requested-model <model-id>]
      [--predecessor-offer <offer-id> --predecessor-attempt <attempt-id>]
      [--reason <utf8-text>]

    nova-work acknowledge --session <path> <write flags> --offer <offer-id> --reply <receipt-id>
      --stage received --provenance <pointer> --provenance-sha256 <hex>

    nova-work acknowledge --session <path> <write flags> --offer <offer-id> --reply <receipt-id>
      --stage accepted --provenance <pointer> --provenance-sha256 <hex>
      --lease-by <duration|UTC-stamp> --lease-default <release|extend-once|escalate:<name>>
      [--observed-model <model-id>] [--bench <bench-id>]
      [--execution <opaque-handle>] [--reason <utf8-text>]

    nova-work decline --session <path> <write flags> --offer <offer-id> --reply <receipt-id>
      --provenance <pointer> --provenance-sha256 <hex> [--reason <utf8-text>]

'--payload' identifies the exact bounded assignment body, not arbitrary follow-up prose; the coordinator validates its SHA-256 and durably retains those exact bounded bytes before acknowledging the offer. It contains task instructions and any allowed non-secret launch plan, while 'request-ref' identifies the dispatch request to a transport/launcher. A recipient must receive the same offer id, node/generation, attempt id, payload digest and profile revision before a receipt can be admitted. '--reserve' is required and positive; capacity is never guessed from a catalog or a prior heartbeat. '--until' is an offer-response deadline and is distinct from request '--deadline' and the accepted lease deadline. Accepted acknowledgements always carry both lease flags as create-if-needed inputs. If a same-holder live lease exists they bind to it without changing its deadline/default; output names the actual lease. This lets concurrent accepted receipts use stable payloads instead of becoming invalid because another acceptance created the lease first.

The canonical JSON payloads have a v1 "op" and ordered canonical fields matching the CLI. 'offer' fields are 'offer_id,node,generation,attempt_id,to,profile,request_ref,payload,payload_sha256,reserve,until,requested_model,predecessor_offer_id,predecessor_attempt_id,reason'. 'acknowledge' fields are 'offer_id,reply_id,stage,provenance,provenance_sha256,lease_deadline,lease_default,observed_model,bench,execution,reason'; fields irrelevant to 'received' are absent; 'accepted' always carries both create-if-needed lease fields. 'decline' fields are 'offer_id,reply_id,provenance,provenance_sha256,reason'. Text is valid UTF-8 within repository control/size bounds; identifiers use one canonical token grammar and timestamps roundtrip as UTC. Absent requested/observed model means unknown, never inferred from CONFIG. Exact list/null/empty semantics and verifier receipt envelope need runtime-intake codec review before pinning.

## Events, indexes, and capacity

Add ordered event kinds ':offer', ':acknowledge', and ':decline'. Every one retains the common event identity (':kind', ':node', ':by', ':stamp', ':clock', ':request', ':generation-owner') and the canonical request fields above. The coordinator additionally records non-request, verified observation fields ':sender', ':receipt-digest', and ':effect'; those are derived by the verifier and must not be accepted from a plain request. ':effect' is one of ':dispatched', ':received', ':accepted', ':accepted-held', ':declined', ':late', or ':duplicate'.

Under the single-writer execution-hold barrier, a successful 'offer' writes ':effect :dispatched', a pending-offer index under both node and friend, and a reservation keyed by '(offer_id, attempt_id)'. An effective hold refuses new dispatch before any reservation. It checks that the profile belongs to the named friend and exact CONFIG revision, permits the requested model if present, is admissible under that profile's policy, and declared free capacity covers the reservation. It does not make the friend willing or available.

'acknowledge --stage received' requires the pending offer's recipient and exact immutable tuple to verify. It records ':received'; it changes neither task lease nor W. A timely 'decline' likewise requires that recipient and tuple, records ':declined', and atomically releases only that still-pending reservation. A decline after accepted ownership or an uncertain execution is ':late' and releases neither active nor uncertain capacity.

'acknowledge --stage accepted' requires an earlier verified ':received', a still-current task generation, an unresolved pending offer, and either no live lease or a live lease held by that same recipient. Under the single writer it first revalidates every effective execution hold. A held acceptance is truthfully retained as ':accepted-held', with its pending reservation intact, and creates no lease, launch, or capacity conversion; later explicit reconciliation decides what to do. Otherwise one accepted mutation envelope records ':accepted' and converts the reservation to **committed** execution capacity, which is not an observation that work is running. If no lease exists, that first accepted envelope creates exactly one existing canonical lease with the supplied deadline/default; W updates from it once. If the same holder's lease exists, the acknowledgement binds assignment to lease in the assignment index, does not alter the lease deadline/default, and does not apply the create-if-needed values. The binding is outside the canonical lease schema. No ':attempt' is written merely because a recipient accepted; any later runtime observation uses the existing/open execution-intake contract and retains its observed handle, model, usage and uncertain outcome independently.

A response deadline does not release a reservation. At 'until', the offer is **overdue-unreconciled**: no new offer or automatic launch is admitted, capacity remains reserved, and any later received/accepted/decline reply is retained as ':late' with no conversion or release. Only the separately specified reconciliation/reassignment path chooses a new action. Likewise, lease expiry removes W membership as the existing lease rules require, while ACTIVE capacity and any uncertain execution remain retained; it is not proof a worker stopped (lines 1344–49).

Receipt id and digest are a second uniqueness key beside request id. Replaying the same request returns the original result under the existing journal rules. A later delivery/reply with the same verified receipt under a fresh request id journals a no-effect ':duplicate' event and durable request disposition without another reservation, lease, launch, or attempt. A verified response after decline, accepted ownership, generation change, offer expiry, or replacement is retained as ':late', linked to its lineage, but cannot create a lease, launch, capacity conversion, or release. Conflicting receipt bytes for one receipt id are refused. This supplies an auditable answer to delayed and duplicate transport without treating silence as failure.

## Refusals, outputs, and review decisions

For new offers, refuse malformed identifiers/stamps/digests, reused offer/attempt identity, changed profile revision, payload mismatch, nonpositive/unavailable capacity, stale generation, predecessor mismatch or cross-holder conflict. For receipt intake, unverified source, malformed data, invalid stage or immutable-tuple mismatch refuse; a verified historical receipt whose offer has since changed disposition follows the late/held rules above rather than being discarded as stale. A verifier outage is 'ACKNOWLEDGE FAIL ...: provenance unverified', leaves canonical state unchanged, and does not turn a bus body into authority. Normal success lines identify 'node', 'offer', 'attempt', 'effect', 'reserved' or 'lease', and 'rev'; late/duplicate lines expose their effect and original lineage.

Reviewer decisions still needed:

1. Pin the authenticated receipt-verifier interface and its bounded public output, including how a coordinator binds a configured friend identity without recording secrets.
2. Approve the assignment-index binding from accepted offer/attempt to the existing holder lease. It deliberately changes neither canonical lease fields nor an existing lease's deadline/default.
3. Pin JSON omission/null/list grammar and byte limits for 'payload', 'reason', receipt provenance, execution handles, and the assignment body.
4. Specify reconciliation, pause, stop, and reassignment policy separately. They alone may clear uncertain capacity or authorize a replacement; this proposal deliberately does not infer any of them.
5. Decide how model-only pool actors fit recipient identity/consent without inventing a friend, as the open CONFIG decision at lines 2478–91 requires.

## Acceptance witnesses

1. An admitted offer with available declared slots produces dispatch plus a pending reservation, but leaves the node state, W, lease index, attempt results, evidence, and completion unchanged.
2. An operator-verified 'received' receipt creates delivery/acknowledgement history only; a copied note or '--as recipient' without verifier proof is refused without canonical writes.
3. An operator-verified accepted receipt after 'received' either creates exactly one linked canonical lease and W entry, or binds a second distinct attempt to the same holder's existing lease without changing its deadline. It converts rather than doubles capacity and records unknown observed model as unknown.
4. Concurrent distinct offers for one node may proceed only for the same holder and explicit capacity; a cross-holder offer or accepted reply cannot create a shadow lease and is refused or retained late according to verified lineage.
5. At response timeout and at lease expiry, no duplicate launch is scheduled and no stopped/completed claim is emitted; uncertain capacity/handle persists until reconciliation.
6. A late accept after decline, replacement, expiry, or task generation change is retained as late, never revives the old lease, releases uncertain capacity, or overwrites the successor attempt.
7. Same request replay returns its earlier success; the same verified receipt under a new request cannot consume capacity again; mismatched bytes for a receipt id are refused.
8. A held accepted receipt is retained with no lease, launch, or capacity release until explicit reconciliation; a replacement then records predecessor offer and attempt while preserving prior raw usage and requested/observed model attribution.
