# nova-tools fixes

Shipped point-release fixes to the kept tools. Fixes to tools that left this repository are in their history at tag v1.6.29.

- **The inventory timeout test reaches the applied-state read again** (shipped). TestInventoryTimeoutFlagGovernsTheConnection parked a raw TCP listener that accepted and never answered, and since nova-config opens its Redis connection through pkg/redisconn.Open (one bounded dial and the HELLO 3 handshake), the verb timed out while connecting and never reached the read of the applied state the test proves. The stalled store now completes the RESP3 handshake and stalls on the read, so the timeout is again `while reading the applied state`; a second case, a store that accepts and never answers the handshake, pins `while connecting`. The product is unchanged: docs/SPEC-CONFIG.md requires pkg/redisconn.Open. From: the coordinator, 2026-10-12: dev's merge queue (run 38247574824, functional 4/6) refused mas-bandwidth/nova-tools#5627 on cmd/nova-config TestInventoryTimeoutFlagGovernsTheConnection, failing 5 of 5 on dev f1ae69f03.
- **A --read-noexec path under an execute-granting root refuses instead of silently executing** (shipped). Landlock's rules are a union: a path is executable when any rule on it or a parent grants fsExecute, so a --read-noexec directory that sat under a root the wall grants execute (a static root, the command's own directory, a --read or a --write) stayed executable in spite of its own no-exec rule. addRules now refuses that policy at build time with reason=sandbox_failed rather than silently letting the execution through, and TestWallAReadNoexecBinaryCannotBeExecuted pins it. From: the seat's unit-coverage survey of nova-tools dev, 2026-10-12: pkg/sandbox/wrap_linux.go's addRules added the no-exec read set last, but the command's own directory is already an execute root, so the no-exec wall silently ran a script under --read-noexec; landed on dev with the-linux-sandbox-wall-is-unit-tested-on-a-landlock-kernel (f1ae69f03, 2026-10-12).
